## D-1: `'P'` / `'G'` タイルを「スプライトの足元が乗るセル」と再定義

**日付:** 2026-05-04
**関連:** v0.1 デプロイ後、Pages 上での実機確認時に発覚

### Why

- 当初実装では `spawnY = spawnRow * TILE_SIZE + TILE_SIZE / 2`（タイル中心）にプレイヤーを配置
- `'P'` が行15（床直上の空中セル）の例: プレイヤー中心 Y=496、プレイヤー高 48 → 足元 Y=520
- 床（行16）の上端 Y=512 に対して **足元が 8px めり込んだ状態でスタート**
- Phaser Arcade Physics はめり込みを解消できず、トンネル現象でプレイヤーが地面を貫通して落ち続ける
- 同様に `'G'` も中心配置だと床から半分埋もれる

### Decision

`GameScene.buildStage()` の Y 計算を、足元基準に変更:

- `spawnY = (spawnRow + 1) * TILE_SIZE - PLAYER_SPRITE_H / 2`
- `goalY  = (goalRow  + 1) * TILE_SIZE - GOAL_SPRITE_H  / 2`

これにより `'P'` / `'G'` タイルは **「スプライトの足元が乗るセル」** という意味になり、スプライト下端 = `(row + 1) * TILE_SIZE` で床にぴったり立つ（または床から `(rows-1 - row) * TILE_SIZE` 浮く）。

ステージ定義 `stage01.ts` の文字配置はそのまま。

### Consequence

- プレイヤー貫通バグ解消、地面の上に正しく立つ
- 既存ステージの `'P'`（行15）・`'G'`（行14）の意図そのままで動作（スポーンは床直上、ゴールは床から 1 タイル分上に浮く）
- 将来ステージ追加時のタイル配置ルールが「スプライトの足元 = タイル位置」で統一される
- リスク: スプライト高がタイル高より大きい場合（`PLAYER_SPRITE_H=48` > `TILE_SIZE=32`）、スプライト上端は配置タイルより上の空中セルにはみ出す。レベル設計時に「足元タイルから上方向に余白を取る」必要あり（v0.2 で他敵キャラ追加時の設計指針）

## D-2: タッチ操作（左 / 右 / ジャンプ）を v0.1 のスコープに追加

**日付:** 2026-05-04
**関連:** v0.1 デプロイ後、シャビが実機（Dev Container 環境）で動作確認時に発覚

### Why

- `requirements.md §3.2` で「モバイルタッチ操作」は v0.2 以降に明示的に除外していた
- しかしシャビの開発環境が Dev Container 内で完結しており、PC ブラウザでのキーボード操作確認手段が事実上存在しない
- スマホで Pages を開いて確認しようとしても、キーボード前提のため操作不能 → **動作確認自体が不可能**
- 「v0.1 を動作確認可能にする」要件と「タッチ操作除外」要件が両立しない

### Decision

最小実装のタッチ操作を v0.1 ホットフィックスに追加:

- 画面下部に半透明の 3 ボタン（左 `←` / 右 `→` / ジャンプ `↑`）を Phaser 固定 UI として配置（`setScrollFactor(0)` + `setInteractive()`）
- `pointerdown` / `pointerup` / `pointerout` / `pointerupoutside` で内部フラグ（`touchLeft` / `touchRight` / `touchJump`）を管理
- `update()` ではキーボード入力と OR 合成（`leftDown = cursors.left?.isDown || touchLeft`）
- クリアテキストを `setInteractive()` 化し、タップでも `scene.restart()` を発火（R キー相当）

### Consequence

- スマホ（タッチ）/ PC（キーボード）どちらでも動作確認・プレイ可能
- `requirements.md §3.2` の除外項目「モバイルタッチ操作」は **本決定で取り下げ**。代わりに「最小限のタッチ操作」が v0.1 スコープに含まれる
- v0.2 でタッチ UX を本格化する際は、ボタン配置・サイズ・押下フィードバックを再設計予定（現状は「動作確認のための最小ボタン」レベル）
- 追加依存ゼロ、CSP 変更なし、外部通信なし。セキュリティ影響軽微

## D-3: リスタート方式を `scene.restart()` から `scene.start('BootScene')` に切替

**日付:** 2026-05-04
**関連:** D-2 後の実機確認で発覚

### Why

- D-2 のホットフィックス後、シャビが Pages 上で再確認したところ「**2 回目以降のリスタートで初回位置から床貫通して落ち続ける**」現象を報告
- 1 回目のプレイは正常に床に立つ（D-1 の修正は効いている）
- 2 回目以降のみ崩れることから、`scene.restart()` 後の物理ワールド再構築タイミングで `staticGroup.create()` で生成された地面 sprite の static body サイズ・位置が完全に確立されないケースを疑う（特に `BootScene.preload()` の `Graphics.generateTexture` 由来テクスチャを参照する場合に顕著）

### Decision

- `update()` 内 R キーの分岐と、タッチクリア時の `handlePointerDown` 分岐の両方で `this.scene.restart()` を `this.scene.start('BootScene')` に置換
- `BootScene → GameScene` の流れで、テクスチャ・物理ワールド・入力プラグインがすべて再初期化される完全再構築方式に変更
- 念のため、`buildStage()` の各地面 sprite と goal sprite に `refreshBody()` を明示呼び出しして、static body のサイズ・位置を確実に再計算

### Consequence

- リスタート後の地面貫通バグを根治（仮説どおりであれば）
- 再構築コストは数 ms 程度増加するが、v0.1 規模では誤差レベル
- design.md §10.1 Q3 で「リスタート方式は `this.scene.restart()` 採用」と決めていたが、本決定で更新。**Why は安定性 > わずかな再構築コスト**
- 副作用: `BootScene` を経由するため、リスタート時に一瞬黒画面（テクスチャ再生成中）が見える可能性。実機で気になれば BootScene の preload 高速化を検討

## D-4: タッチ UI を 3 ボタン → 画面左右半分の長押し + 短タップでジャンプ に変更

**日付:** 2026-05-04
**関連:** D-2 後の実機 UX レビュー

### Why

- D-2 で導入した画面下部 3 ボタン（左 / 右 / ジャンプ）はゲーム画面を圧迫し、視認性も低かった
- シャビからの指示: 「タッチボタンは表示せず、右側左側の長押しで進む、短いタッチでジャンプにして」
- スマホでの自然な操作（画面全体をタッチ領域として使う）を最小実装で提供する

### Decision

- 3 ボタン UI を全廃
- `this.input.on('pointerdown' / 'pointerup' / 'pointerupoutside')` でグローバル pointer ハンドラを実装
- 押下時に `pointer.x < this.scale.width / 2` で左右半分を判定し、`TOUCH_HOLD_MS=180` 経過後も押されていれば移動モード（`touchLeft` / `touchRight` 立て）
- `TOUCH_HOLD_MS` 未満で離されたら `touchJumpRequested` を 1 フレーム立てて `update()` で消費
- クリア中は pointerdown でリスタート（クリアテキストの `setInteractive()` は廃止し、画面全体タップで restart 受付）
- 閾値 `TOUCH_HOLD_MS` は `gameConfig.ts` に集約（ハードコード禁止ルール）
- 操作説明テキストを「PC: ←/→ Space/↑ R   スマホ: 画面左右の長押しで移動 / タップでジャンプ」に更新

### Consequence

- 画面が広く使え、ゲーム画面の視認性が改善
- タッチ操作の学習コストは「左右半分長押し / タップでジャンプ」だけで覚えやすい
- 前回 Q12（バックグラウンド復帰時の押下固着） / Q13（クリア時のボタン重複発火）は本変更で実質解消（タイマーベース + 画面全体ハンドラのため、ボタン領域重複が起きない）。Q12 は依然 v0.2 で `Phaser.Scenes.Events.SLEEP/PAUSE` 対応推奨
- 副作用: PC マウスクリックでも同じハンドラが発火する。意図せず移動 / ジャンプが発生するが、PC ユーザーはキーボードを使う前提なので実害軽微

## D-5: リスタートを `window.location.reload()` による完全ページリロードに変更

**日付:** 2026-05-04
**関連:** D-3 後の実機確認で再発

### Why

- D-3 で `scene.restart()` → `scene.start('BootScene')` + `refreshBody()` 明示に切り替えたが、シャビ実機確認で **2 回目以降のリスタートで床貫通が再現**
- BootScene 経由でも static body の再構築タイミング問題が解消されない可能性
- Phaser のシーンマネージャ周りで何らかの状態残留があると推測されるが、ローカル動作確認手段なし（D「dev サーバー起動禁止」運用のため）で深掘りコスト高
- 「リスタートできない」のは v0.1 受入条件 §7「R キーで `GameScene` がリスタートし、再度プレイできる」を満たさないため、最終手段でも根治を優先

### Decision

- `fullRestart()` を `window.location.reload()` に変更
- ブラウザのページリロードによって、Phaser.Game / シーンマネージャ / 物理ワールド / テクスチャマネージャ / 入力プラグインがすべて初期状態から再構築される
- `update()` 内 R キー分岐とタッチクリア時 `handlePointerDown` 分岐の両方が同じ `fullRestart()` を呼ぶ構造はそのまま維持
- CSP 影響なし（同一オリジンのリロード、`default-src 'self'` 範囲内）

### Consequence

- リスタート後の状態残留リスクをハードウェアレベル含めて完全排除
- 副作用: リスタートに数百 ms 〜 1 秒程度のロード待ちが発生する（バンドル 1,486 kB の再ダウンロードはキャッシュで軽減されるが、JS パース・Phaser 初期化分は再実行）
- design.md §10.1 Q3 の「リスタート方式」決定は D-3 → D-5 で 2 段階更新。**Why は安定性 > リスタート所要時間**
- 根本原因（なぜ scene.start('BootScene') でも 2 回目から body が壊れるか）は v0.2 で時間が取れるときに調査。Q17 として記録

## D-6: プレイヤー色を `0xff3b30` → `0xc0392b` に変更

**日付:** 2026-05-04
**関連:** シャビ実機確認の視認性フィードバック

### Why

- シャビから「赤色が眩しすぎる」「もう少しだけ暗い赤に」と指示
- 元の `0xff3b30` は iOS システムレッド相当で、彩度・明度が高くスマホ実機で目に刺さる

### Decision

- `gameConfig.ts` の `PLAYER_COLOR` を `0xff3b30` → `0xc0392b`（深めの赤、Flat UI Pomegranate 系）に変更
- 他の色（`GROUND_COLOR=0x8b4513`、`GOAL_COLOR=0xffd700`、`BG_COLOR='#5c94fc'`）は据え置き

### Consequence

- スマホ実機での視認性疲労が軽減
- v0.2 で実画像アセット導入時にスプライト本体に置き換わるため、本決定はプレースホルダ期間のみ有効
